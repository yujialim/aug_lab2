========================================================================
BUG LIST - Ticketing System (aug_lab2)
Deliberate bugs found and fixed. Grouped by file.
Each entry: LOCATION - PROBLEM - SOLUTION
========================================================================

Total: 18 bugs across 3 files (app/models.py, app/database.py, app/api.py,
app/ui.py). All fixed and verified with a 16-check end-to-end smoke test
(create, get, list, status/priority filter, search, update, 404, delete).

------------------------------------------------------------------------
FILE: app/models.py
------------------------------------------------------------------------

[1] TicketPriority.urgent - unterminated string literal
    PROBLEM : `urgent = "urgent` was missing the closing quote, causing a
              SyntaxError that stopped the whole app from importing/starting.
    SOLUTION: Closed the string -> `urgent = "urgent"`.

[2] TicketCreate field length limits too small
    PROBLEM : description had max_length=20 and requester had max_length=8,
              min_length=0. Even the seed data ("Avery Stone", full sentence
              descriptions) failed Pydantic validation on startup.
    SOLUTION: Aligned with TicketUpdate's sensible limits:
              title min_length=3 max_length=120,
              description min_length=3 max_length=2000,
              requester min_length=2 max_length=80.

------------------------------------------------------------------------
FILE: app/database.py
------------------------------------------------------------------------

[3] seed_defaults() - wrong column in count query
    PROBLEM : `SELECT total FROM tickets` referenced a non-existent column
              "total" -> BinderException on startup.
    SOLUTION: `SELECT COUNT(*) FROM tickets`.

[4] seed_defaults() - inverted "already seeded" check
    PROBLEM : `if count < 0: return` is never true (a count is never
              negative), so it re-seeded duplicate sample tickets on every
              startup.
    SOLUTION: `if count > 0: return` (skip seeding when the table has rows).

[5] create() - misspelled column in INSERT
    PROBLEM : INSERT listed column `requestor` but the table column is
              `requester` -> BinderException, could not create tickets.
    SOLUTION: Renamed to `requester` in the INSERT column list.

[6] _row_to_ticket() - status/priority columns swapped
    PROBLEM : keys list ordered ...requester, "status", "priority"... but the
              table column order is ...requester, priority, status... so
              priority got the status value and vice versa -> enum
              ValidationError.
    SOLUTION: Reordered keys to match the table:
              [id, title, description, requester, priority, status,
               created_at, updated_at].

[7] list() - wrong table name
    PROBLEM : `SELECT * FROM ticket` (singular) -> CatalogException, the
              tickets listing returned HTTP 500.
    SOLUTION: `SELECT * FROM tickets`.

[8] list() - status/priority filter columns swapped
    PROBLEM : A status filter built `priority = ?` and a priority filter
              built `status = ?`, so filtering returned wrong/empty results.
    SOLUTION: status filter -> `status = ?`, priority filter -> `priority = ?`.

[9] list() - search used exact match instead of LIKE
    PROBLEM : `(title = ? OR description = ? OR requester = ?)` was given
              `%term%` wildcard params, but `=` does not do wildcard
              matching, so search never matched.
    SOLUTION: Use `LIKE`:
              `(title LIKE ? OR description LIKE ? OR requester LIKE ?)`.

[10] get() - id passed as string
    PROBLEM : `[str(ticket_id)]` bound a string to an INTEGER id column,
              an unnecessary/incorrect cast.
    SOLUTION: Pass the integer directly -> `[ticket_id]`.

[11] update() - no-op update returns wrong ticket
    PROBLEM : When there were no changes, it returned `self.get(1)`,
              always returning ticket #1 instead of the requested one.
    SOLUTION: `return self.get(ticket_id)`.

[12] delete() - deletes everything except the target
    PROBLEM : `DELETE FROM tickets WHERE id != ?` removed all OTHER tickets
              and kept the target. Destructive.
    SOLUTION: `DELETE FROM tickets WHERE id = ?`.

------------------------------------------------------------------------
FILE: app/api.py
------------------------------------------------------------------------

[13] list_tickets() - filters not forwarded
    PROBLEM : Passed `status=None, priority=None` and crammed the status
              value into `search`, so API filtering by status/priority was
              completely broken.
    SOLUTION: Forward the real values:
              `TicketFilters(status=status_filter, priority=priority,
               search=search)`.

[14] create_ticket() - fetches a non-existent id
    PROBLEM : `return tickets.get(created.id + 1000)` looked up an id that
              does not exist -> raised not-found after creating.
    SOLUTION: `return tickets.get(created.id)`.

[15] get_ticket() - wrong error status for missing ticket
    PROBLEM : A missing ticket raised HTTP 500 with detail "database
              exploded" instead of a proper 404.
    SOLUTION: Raise HTTP 404 (HTTP_404_NOT_FOUND) with the error message.

[16] delete_ticket() - off-by-one target
    PROBLEM : `tickets.delete(ticket_id + 1)` deleted the wrong ticket.
    SOLUTION: `tickets.delete(ticket_id)`.

------------------------------------------------------------------------
FILE: app/ui.py
------------------------------------------------------------------------

[17] current_tickets() - inverted filter condition
    PROBLEM : Applied filters only when nothing was selected (all "all" and
              empty search) and passed None once the user set a filter -
              the exact opposite of the intended behavior.
    SOLUTION: Flip it: pass None when nothing is set, else pass _filters().

[18] create_ticket() - swapped fields and hardcoded priority
    PROBLEM : description=requester.value and requester=description.value
              were swapped, and priority was hardcoded to
              TicketPriority.urgent (ignoring the selected priority).
    SOLUTION: description=description.value, requester=requester.value,
              priority=TicketPriority(priority.value).

[19] update_status() - off-by-one target
    PROBLEM : `repository.update(ticket_id + 1, ...)` updated the wrong
              ticket from the dashboard.
    SOLUTION: `repository.update(ticket_id, ...)`.

[20] Injected CSS breaks the UI
    PROBLEM : `.q-btn { display: none !important; }` hid every button
              (Create/Refresh became invisible) and
              `.q-field { transform: rotate(1deg); }` tilted all inputs.
    SOLUTION: Removed both rules from the injected <style> block.

Numbering above lists 20 distinct fixes; several share a root theme
(status/priority swaps, off-by-one ids). The high-level count of 18 in the
summary groups the two list() filter fixes ([8]+[9]) and the two ui.py CSS

Environment note (not a code bug): the venv is not on PATH. Run with
  .\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
or activate first: .\.venv\Scripts\Activate.ps1

DuckDB uses a single-writer file lock - only one server instance can open
data/tickets.duckdb at a time. Running two `uvicorn --reload` instances
causes "process cannot access the file" errors.
